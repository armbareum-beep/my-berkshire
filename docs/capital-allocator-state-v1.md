> 이 문서 하나만 읽으면 자본배분 기능이 **지금 어떻게 생겼고, 무엇이 없는지** 알 수 있다.

## 1. 제품 질문

> **지금 새 돈이 생기면 어디에 넣어야 하는가?**

이 앱은 좋은 기업을 찾아주지 않는다. 기업은 사람이 고르고, **가격과 배분만 시스템이 계산한다**
(PRD v0.3 §3.1). 이 분업이 아래 모든 설계의 뿌리다.

## 3. 밸류에이션 모형 — 기간 종료 배수

`src/lib/finance/expectedReturn.ts`

```text
미래가격  = 현재 이익력 × (1 + 성장률)^Y × 종료 배수
매수가    = 미래가격 ÷ (1 + 요구수익률)^Y
기대 CAGR = (미래가격 ÷ 현재가)^(1/Y) − 1
```

**지금 PER 은 보지 않는다.** 저PER 을 우대하지도, 고성장을 우대하지도 않는다 — 성장률과
종료 배수가 곱해져 **기대 CAGR 하나로 뭉개지고**, 가치주와 성장주가 같은 잣대로 경쟁한다.

> ⚠️ **스타일에는 중립이지만 낙관에는 중립이 아니다.** 성장률과 종료 배수 둘 다 사용자
> 가정이고 곱해진다. 둘 다 후하게 넣으면 반드시 이기고, 앱은 현실성을 검사하지 않는다.
> 두 가정이 같은 방향으로 틀리면 오차가 곱으로 커진다.

### 앱에 모형이 두 개 있다 — 섞지 말 것

| | `intrinsic.ts` | `expectedReturn.ts` |
|---|---|---|
| 모형 | 고든 성장(영구) | 기간 종료 배수 |
| 쓰는 곳 | 종목 상세 "내재가치" | **자본배분** |
| 성장률 의미 | 영구 성장률 (g < r) | 향후 Y년 이익 CAGR |
| 저장 컬럼 | `discount_rate`·`growth_rate` | `er_*` |

성장률의 의미가 달라 컬럼을 재사용하면 **조용히 틀린 값**이 나온다. 그래서 `er_` 접두사로 분리했다.

## 4. 배분 로직 — 관문 셋

`src/lib/allocate.ts:planAllocation`

```text
1. 탈락   기대 CAGR < 요구수익률           → 배분 0
2. 순서   가중치 = 1 + (기대CAGR − 요구수익률) × 10
3. 한도   기대 CAGR ≥ 요구수익률 + 3%p     → 매수 상한이 목표비중 → Soft Cap

최종 가중치 = 목표 부족분 × 캡 계수 × 매력도
```

| 현재 비중 | 판정 | 화면 표기 |
|---|---|---|
| 목표 이하 | 정상 매수 | 살 수 있음 |
| 목표 초과, 허들 통과 | Soft Cap 까지 매수 | 더 살 수 있음 |
| 목표 초과, 허들 미달 | 우선순위 하향 | 뒤로 밀림 |
| Soft Cap ~ Hard Cap | 강한 감액 | 기다림 |
| Hard Cap 이상 | 차단 | 한도 초과 |

**목표비중이 천장이다.** 기대 CAGR 이 40%여도 무한정 못 산다 — "싸다는 이유로 무한
물타기하지 않는다"(PRD §7). 그래서 경쟁은 "누가 제일 매력적인가"가 아니라
**"누가 자기 목표를 먼저·많이 채우는가"** 다.

매도는 계산하지 않는다(buy-only). 기회가 없으면 현금을 남긴다.

## 5. 가정 입력 — 과거는 앱이, 미래는 사람이

`src/components/stocks/ExpectedReturnWizard.tsx` · `src/lib/finance/pastAnchors.ts`

```text
1/3  앞으로 N년, 이익이 얼마나 늘까요?   ← 성장률
2/3  N년 뒤 시장이 몇 배를 줄까요?        ← 종료 PER
3/3  확인 (+ 고급: 이익력·보유기간·요구수익률)
```

각 단계에 **"앱이 아는 사실"** 을 곁에 둔다 — 과거 EPS CAGR, PER 밴드(평균·최저·최고·현재).

> **입력칸은 비워둔다.** 과거 성장률을 기본값으로 채우면 사용자가 그대로 저장해버려
> 결국 앱이 예측한 것과 같아진다. 사실 옆에는 "그대로 믿지 말라"는 경고를 붙인다.

적자 해는 계산에서 빼고, 흑자 해가 하나뿐이거나 PER 표본이 2년 미만이면 **숫자를 만들지 않는다.**

## 6. 요구수익률 = 난이도

`src/lib/hurdle.ts` — 관대 8% / 표준 12% / 엄격 15% + 직접 입력.

```text
우선순위: 종목별 er_required_return > holdings.required_return > 코드 기본값 12%
```

축하 매트릭스(`celebration.ts`) 준수: 허들을 **정하는 것**과 못 넘겨 **안 사는 것**은
통제 가능한 결정이라 축하 대상이지만, "허들을 넘긴 종목이 생겼다"는 주가 하락의 결과일 수
있어 **시장발**이다. 그래서 난이도는 표시만 하고 어떤 축하 신호도 만들지 않는다.

## 7. 데이터

새 테이블은 만들지 않았다. 기존 테이블에 컬럼만 얹었다(스펙 §13.2).

| 대상 | 용도 |
|---|---|
| `valuation_assumptions.er_*` | 기대수익률 가정(이익력·성장률·종료배수·기간·요구수익률) |
| `holdings.required_return` | 전사 기본 요구수익률. null = 12% |
| `holdings.investable_cash` | 투자 가능 현금 **₩ 저장**, 읽을 때 환산. null = 보유 현금 전액 |
| `holdings.target_weights` | 목표비중. **평면**(`{"META":{"target":0.15}}`) 또는 레거시 2층(숫자) |
| `watchlist.status` | `APPROVED`(배분 후보) / `WATCH`(관심만). 화면에서 직접 토글하지 않는다 — 목표비중을 정하면 자동 승격 |

### 배분 대상은 목표비중 하나로 정해진다

> **목표비중을 정한 종목이 배분 대상이다. 안 정했으면 대상이 아니다.**

한때 "후보(Approved Universe)"를 산업별로 고르는 섹션이 설정 화면에 따로 있었지만,
목표비중을 검색형으로 바꾸며 **비중을 정하면 자동으로 후보가 되도록** 하면서 같은 것을
두 번 묻는 자리가 됐다(같은 종목이 한 화면에 두 번, 하나는 산업별 긴 리스트). 걷어냈다.

"배분에서 빼기"도 따로 없다 — 목표비중 0 이면 배분되지 않는다.
산업별 쏠림은 조회 화면(`/allocation/sector`)이 본다.

### 목표비중 두 형식 공존

`src/lib/targetWeights.ts` 가 값의 타입으로 판별한다(숫자 = 레거시, 객체 = 평면).
읽기는 둘 다 되고, **저장하면 평면으로 넘어간다** — 첫 저장이 곧 이사다.

합계 규칙이 다르다: 레거시는 정규화, 평면은 **합이 1 미만이면 그대로 둔다**(나머지는 현금).

## 9. 손대면 안 되는 것

- **`AllocateStatus` 문자열 값** — 계산 로직과 테스트가 걸려 있다. 사람이 읽는 말은
  `components/allocate/statusMeta.ts` 한 곳에서만 바꾼다.
- **`growth_rate` 와 `er_expected_growth` 혼용** — 의미가 다르다(§3).
- **`category_targets` 삭제** — `/allocation/[tag]` 조회와 레거시 환산이 읽는다.
- **투자 가능 현금을 표시통화로 저장** — ₩ 로 저장하고 읽을 때 환산해야 한다(§16.3).
