# Allocate 레일 v2 — 고르게 하지 않는다

> 작성: 2026-08-13 (2026-08-14 §4·§5 추가)
> 선행 문서: `allocate-redesign-v1.md`(같은 날 구현 완료) · `user-rails-v1.md` §1-1 · `design-strategy-v1.md` §4
> 결정 사항: `/allocate` 를 **한 화면 4단계 레일**로 전환 · `/allocate/plan` 흡수 ·
> 순위를 레일 3단계로 편입 · 묶음(주식/ETF) 선택 도입

---

## 0. v1 을 하고도 왜 또 바꾸나

v1 은 "한 화면 한 가지 일"을 **화면을 쪼개서** 풀었다 — 보기(`/allocate`) / 실행(`/allocate/plan`)
/ 설정(`/allocate/settings`). 체크리스트는 통과했는데 쓰는 느낌은 나아지지 않았다.

사용자 피드백: **"단계별로 게임하듯이 했으면 좋겠다. 해야 할 게 한 가지씩 나왔으면 좋겠다."**

### v1 이 남긴 것

| 증상 | 코드 근거(v1 시점) |
|---|---|
| 첫 화면이 **답이 아니라 입력값**을 크게 띄운다 | 히어로 = 투자 가능 현금. 사용자가 이미 아는 숫자다 |
| 같은 정보가 한 화면에 **두 번** | "오늘의 1순위" 카드 = "살 곳 순위" 1번 줄(로고·이름·`현재→목표` 동일) |
| 정작 답("어디에 얼마")은 **한 화면 더** | `/allocate/plan` |
| 그 화면이 **묻는 게 없다** | 금액이 투자 가능 현금으로 이미 채워져 있어 그대로 두고 결과만 봄 |

**뿌리 원인:** 화면을 쪼갠 건 맞는데, 쪼갠 조각들을 **동시에 늘어놓았다.** 카드 3개가 한
화면에 있으면 사용자는 매번 "이 중 뭘 해야 하지"를 고른다. 카드 수를 줄여도 *고르는 일*
자체는 사라지지 않는다.

> **선택지를 안 주는 게 친절이다** — `user-rails-v1.md` 서문.

이 앱은 이미 같은 문제를 거래 입력에서 풀었다(`user-rails-v1.md` §1-1):
*"폼 한 장에 다 넣으면 회계 입력이고, 한 번에 하나씩 물으면 딜 체결이다."*
자본배분만 그 레일을 안 타고 있었다.

## 1. 목표 상태

```text
┌ 1/4 ●○○○ ──────┐  ┌ 2/4 ○●○○ ─────┐  ┌ 3/4 ○○●○ ──────┐  ┌ 4/4 ○○○● ─────┐
│ 얼마를 넣을까요  │→ │ 어디에 넣을까요 │→ │ 이렇게 나눕니다  │→ │ 몇 주씩 살까요 │
│ [₩50,000,000]  │  │  주식 7        │  │  기대수익률 순   │  │ META  ×34주   │
│ +1만 +10만     │  │   1순위 META   │  │ 1 META  +₩12M   │  │ BRK.B ×12주   │
│                │  │   기대 17.2%   │  │   목표 10%까지  │  │ ───────────  │
│                │  │  ETF·기타 3    │  │   3%p 부족      │  │ 합계 ₩47.9M   │
│ [ 다음 ]       │  │   1순위 SPY    │  │ 2 BRK.B +₩8M    │  │ [이 계획으로  │
│                │  │   목표까지 −4% │  │  [ 이대로 진행 ] │  │      등기]    │
└────────────────┘  └───────────────┘  └─────────────────┘  └───────────────┘
                       탭하면 자동 전진                              ↓ 도장 ✓
                                                      "자본배분이 등기되었습니다"
```

화면은 **하나**다. 단계가 넷일 뿐이다. 묶음이 하나뿐인 사용자에겐 2단계를 건너뛴다 —
고를 게 없는 질문은 마찰일 뿐이라 3단계 레일이 된다.

### 네 단계는 각각 다른 일을 한다

| 단계 | 묻는 것 | 왜 합칠 수 없나 |
|---|---|---|
| 1 | 얼마를 넣을까 | 사용자만 아는 값 |
| 2 | 주식이냐 ETF냐 | **정렬 기준이 다른 두 묶음**이라 한 줄로 세울 수 없다(§4) |
| 3 | 어디에 얼마씩 | 고른 묶음의 순위 + 금액 |
| 4 | 몇 주씩 | 금액은 주가로 나눠떨어지지 않는다. 계획은 **주수**로 등기된다 |

4단계가 3단계의 요약이었다면 뺐다. 실제로 다른 숫자라서 남긴다 — v1 의 "1순위 카드 =
순위 1번 줄" 중복을 되풀이하지 않기 위한 기준이다.

## 2. 부품을 새로 만들지 않았다

거래 입력 위저드의 부품을 그대로 쓴다. 같은 부품을 쓰므로 두 여정이 같은 앱처럼 느껴진다.

| 부품 | 출처 | 하는 일 |
|---|---|---|
| `StepShell` | `components/transactions/wizard/` | 진행 점 ●●● · ‹ 뒤로 · 큰 질문 |
| `NumberPadField` | `components/ui/NumberPad` | 키패드 시트(토스 송금 무드) |
| `SuccessOverlay` | `components/transactions/wizard/` | 도장 ✓ + "등기되었습니다" |
| `QuickAdd` | `components/ui/QuickAdd` | +1만 · +10만 알약 |

`StepShell` 에 `className` 하나만 더했다(탭바 띄우는 단계의 아래 여백). 그 외 공용 부품은
건드리지 않았다.

**엔진에 더한 것은 `PlanOptions.eligible` 하나뿐이다**(§5). 계산 규칙 — 캡·상한·매력도·
우선순위 — 은 그대로고 `rankRows`·`expectedReturn`·`hurdle` 도 손대지 않았다. 옵션을
생략하면 이전과 완전히 같은 경로라 기존 테스트 465개가 그대로 통과한다.

## 3. 탭바 — 1단계에만 둔다

`design-strategy-v1.md` §4 는 "여정 중" 화면에 탭바를 두지 말라고 한다. 그런데 `/allocate`
는 하단 탭 자체라, 전 단계에서 없애면 진입하자마자 갇힌다.

그래서 **1단계에만 탭바를 둔다.** 여기까지가 평시 화면이고, 금액을 확정하고 넘어가는
순간부터 여정이다. 관문 화면(시세 없음 · 목표비중 없음)도 아직 평시라 탭바를 남긴다.

## 4. 순위는 레일 **안에** 있다

이 문서 초판은 순위 목록을 `/allocate/ranking` 조회 화면으로 빼고 1단계 하단에 작은
텍스트 링크로 걸었다. **사실상 안 보였다.** 사용자 피드백: *"순위에 대한 로직은 왜 안 떠?"*

지금은 **3단계가 곧 순위다.** 번호 · 정렬 기준 · 기대수익률이 금액과 같은 줄에 있다.
"왜 이 순서인지"가 배분과 분리되지 않는다.

```text
기대수익률 순
1  META   살 수 있음   목표 10%까지 3%p 부족   7% → 10% · 기대 17.2%   +₩12,000,000
2  BRK.B  살 수 있음   목표 10%까지 1%p 부족   9% → 10% · 기대 13.8%   +₩8,000,000
```

### 주식과 ETF 를 한 줄로 세우지 않는 이유

`lib/allocateRanking.ts` 에 이미 있던 판단이다 — 주식은 **기대수익률**, ETF 는 **목표 미달**로
줄 세운다. 기대수익률 모형이 개별기업에만 성립하기 때문이다(`valuationApplies`). 기준이
다른 둘에 연속 번호를 매기면 비교 가능한 척이 된다.

예전엔 이걸 가로 스와이프로 갈라 놨다(숨은 제스처). 레일에서는 **아예 고르고 들어간다** —
2단계가 그 선택이고, 고른 쪽에만 돈이 간다. 선택 카드에 각 묶음의 1순위를 미리 보여줘서
고를 근거를 그 자리에서 준다.

**`/allocate/ranking` 과 `AllocateRanking` 은 삭제했다** — 레일 3단계가 같은 목록을 같은
순서로 보여주므로, 두 곳에 두면 v1 의 중복을 되풀이하는 것이다.

## 5. 고른 쪽에만 넣되, 비중은 전체 기준

엔진에 `PlanOptions.eligible` 을 더했다(`src/lib/allocate.ts`). 이번 배분에서 **돈을 받을 수
있는** 종목을 가리는 술어다.

```ts
planAllocation(rows, amount, { eligible: (t) => pickedKeys.has(t.key) })
```

**목록을 걸러서 넘기면 안 된다.** `portfolioValue` 가 그 부분집합의 합이 되어 현재 비중이
부풀려지기 때문이다 — 주식만 넘기면 주식 비중이 전부 100% 쪽으로 뜬다. 그래서 대상은
전부 넘기고 가중치만 0으로 만든다.

| 유지되는 것 | 달라지는 것 |
|---|---|
| 분모(전체 자산) · 현재 비중 · 상태 · 캡 판정 | 안 고른 묶음의 배분액 = 0 |

받지 못한 돈은 `remainingCash` 로 정직하게 남는다 — 안 고른 묶음으로 흘러가지 않는다.
회귀 테스트 4개로 못박았다(`allocate.test.ts` "eligible(묶음 선택)").

## 7. 게이미피케이션 매트릭스 통과 확인

`gamification-honest-roman-v1.md` §2 의 축하 매트릭스를 통과하는지 확인했다.

- 도장 ✓ 연출이 축하하는 것은 **"자본배분 계획을 세웠다"** — 규율 이행(✅ 축하 OK 목록의
  "자본배분 계획 완수"와 같은 줄)이다.
- **시장 결과에는 아무 연출도 붙이지 않는다.** 배분 결과 화면의 숫자(비중·기대수익률·
  남는 현금)는 그대로 정직하게 보여준다. confetti·파티클 없음(신규 의존성 0).
- "살 곳이 없어요"를 숨기지 않는다 — 3단계에서 그대로 말하고 현금으로 두는 게 맞다고 한다.
- 순위 번호 옆에 **정렬 기준을 항상 밝힌다**(§4). 기준 없는 순위는 계기판에 섞인 거짓이다.

> 로망은 **연출**(도장·등기 카피)에, 정직은 **계기판**(숫자)에.

## 9. 묶음을 렌즈로 넓힌다 (2026-08-14 추가)

> 이 절은 §1·§5·§6 을 갱신한다. 레일은 **5단계**가 되었고, 2단계였던 "주식이냐 ETF냐"는
> 3단계 "어느 묶음이냐"로 바뀌었다.

### 9.1 왜

사용자 지적: **"국가별, 산업별 비중 구하는 건 왜 없어? 그리고 어디에 넣을까요도
바꿔야지 않아?"**

두 문장이 한 덩어리다. 1단계에서 국가·산업 비중을 **보게** 되면, 배분도 같은 축으로
**고를** 수 있어야 한다. 보는 축과 고르는 축이 다르면 "미국이 모자라네"까지 읽고도
할 수 있는 건 "주식/ETF" 뿐이라 손이 멈춘다.

### 9.2 1단계 — 세 각도로 정한다

```text
┌ 1/5 ●○○○○ ─────────────────────┐
│ 얼마나 들고 갈까요               │
│ [ 유형 | 국가 | 산업 ]           │  ← 탭. 진실은 하나, 축만 바뀐다
│  ◕  미국 60%  한국 15%  현금 25% │
│  미국 ›   지금 52%  [60] %       │  ← 셋 다 여기서 민다
│  한국 ›   지금 23%  [15] %       │
│  현금     지금 25%   25%         │  ← 나머지(자동)
└─────────────────────────────────┘
```

**세 축 모두 그 자리에서 민다.** 처음엔 국가·산업을 읽기 전용으로 냈다가 되돌렸다 —
*"국가별 산업별은 왜 바로 바꿀 수 없냐니까?"* 사람이 하는 판단은 "미국을 60%까지
올리자"이지 "미국이 60%가 되도록 META 와 NVDA 를 각각 얼마로 맞추자"가 아니다.
그 환산은 **코드가 할 일**이고 `scaleGroupTarget` 이 이미 한다.

못 미는 줄은 둘뿐이다 — **현금**(목표를 안 채운 나머지라 정의상 결과값)과
**기타·미분류**(구성이 유동적이라 밀면 엉뚱한 종목이 딸려간다). 둘 다 입력칸 대신
이유를 한 줄로 붙인다. 칸이 없는데 설명도 없으면 고장으로 읽힌다.

### 9.2.1 축 고정 — 한 축을 밀어도 다른 축은 안 움직인다

처음엔 늘어난 몫을 **현금에서** 가져왔다. 그래서 미국을 밀면 미국 ETF 목표도 같이 커져
유형 비중이 따라 움직였다. 사용자 지적: *"유형 국가 산업이 모두 연동되어 있어?
연동 안 되게 하는 건 어때?"*

**세 축을 따로 저장하는 길은 없다.** 같은 종목을 세 번 세는 것이라 서로 모순될 수 있고
(미국 보유가 전부 주식인데 "주식 45% · 미국 60%"는 성립하지 않는다), 그러면 엔진이
하나만 따르고 나머지 둘은 장식이 된다 — §13.2 가 은퇴시킨 2층 구조의 3층 판이다.

대신 **부족분을 어디서 가져오는지**를 바꿨다(`lib/targetLens.ts:scaleGroupLocked`).

```text
  미국 = META(주식 30%) + SPY(ETF 20%)      한국 = 삼성(주식 15%) + KODEX(ETF 10%)

  미국 50% → 60%
    주식 칸: META 30→36  ⇄  삼성 15→9      (주식 합 45% 그대로)
    ETF  칸: SPY  20→24  ⇄  KODEX 10→6     (ETF  합 30% 그대로)
  결과: 미국 60 · 한국 15 · 현금 25 — 유형도 현금도 안 움직였다
```

스트라텀별 몫은 **묶음 안의 구성 비율 그대로** 나눈다(위에서 6:4). 그래야 "미국을
올렸더니 미국 안에서 ETF 비중만 커지는" 일이 없다.

| 미는 축 | 고정하는 축 | 왜 |
|---|---|---|
| 국가 · 산업 | **유형** | 배분 엔진이 주식과 ETF 를 다르게 다룬다. 여기가 흔들리면 가장 곤란하다 |
| 유형 | **국가** | 대칭. 같은 나라 안에서 주식↔ETF 가 맞바뀐다 |

### 9.2.2 늘 되지는 않는다 — 깨지면 말한다

한국에 ETF 가 없으면 ETF 칸에서 가져올 데가 없다. 그때는 **요청대로 옮기되 상계하지 못한
양을 `shortfall` 로 돌려주고, 토스트가 말한다** — *"미국 목표 60.0% · 유형도 4.0% 움직였어요."*

조용히 덜 옮기면 요청한 60% 가 안 되고, 조용히 다 가져가면 고정이 깨진 걸 모른다.
**둘 다 아니고, 요청은 지키되 깨진 만큼을 말한다.**

여러 종목이 동시에 움직이므로 되돌리기는 **한 번에**(`restoreTargets`) 낸다.

### 9.2.3 현금이 편집 가능해진 이유

고정을 켜면 어느 묶음을 밀어도 현금이 안 움직인다 — 그게 고정의 정의다. 그런데 그러면
**현금 수준을 바꿀 길이 사라진다.** 예전엔 "목표를 안 채우면 나머지가 현금"이라 다른 줄을
밀어 간접으로 조절했기 때문이다.

그래서 현금 줄을 열었다(`setCashTargetAction`). 저장 형식은 그대로 — 현금은 여전히
저장되지 않고, 종목 목표를 통째로 비례 조정해 `1 − Σ목표` 가 요청한 값이 되게 한다(§16.2).
전 종목이 같은 비율로 움직이므로 **세 축의 상대 모양이 전부 보존된다.** 통화에 배정한
몫(`CASH:USD`)도 현금이라 그보다 작게는 못 줄인다.

### 9.2.4 종목 하나는 고정하지 않는다

`setTargetWeight`(계층 화면의 종목 줄)에는 상계를 걸지 않았다. *"META 를 36% 로"* 라고
했는데 손대지 않은 NVDA 가 몰래 줄면 그게 더 놀랍다. 종목을 올리면 그만큼 **현금에서**
오고, 합이 100% 를 넘으면 막힌다(§9.6). 화면 각주가 그 사실을 말한다.

역할이 이렇게 갈린다 — **묶음은 1단계에서 축을 고정한 채, 그 안의 종목 비율은 계층
화면에서 현금과 주고받으며.** 묶음 목표를 계층 화면에도 두면 같은 값을 두 곳에서 정하게
되어 *"비중 바꾸는 곳이 너무 많다"* 로 돌아간다.

### 9.3 3단계 — 유형·국가·산업 중 한 묶음

`lib/allocateBuckets.ts` 가 순위 목록을 렌즈로 묶는다. 순서는 **목표 미달 합 내림차순** —
"어디에 넣을까"의 답이 곧 목록 순서여야 고르는 일이 쉬워진다. 태그가 없어 모인
묶음(기타·미분류)은 구성이 유동적이라 맨 아래로 내린다.

### 9.4 묶음 안에서 기준이 갈리는 문제

"미국"을 고르면 미국 주식과 미국 ETF 가 함께 들어온다. 둘은 정렬 기준이 다르므로(§4)
이어진 번호를 매기면 비교 가능한 척이 된다. 그래서 **묶음 안을 두 섹션으로 갈라 각각
1번부터** 센다.

```text
4/5  이렇게 나눕니다 — 미국
     기대수익률 순
      1 META   +₩12M
      2 BRK.B  +₩8M
     목표 미달 순
     (기대수익률 모형을 쓸 수 없어 목표비중으로만 판단해요)
      1 SPY    +₩5M
```

유형으로 골랐으면 한 섹션이 늘 비어 예전과 똑같이 한 목록만 보인다.

### 9.5 3단계를 건너뛰는 조건이 달라졌다

예전엔 "주식·ETF 중 하나만 있으면" 건너뛰었다. 지금은 **어느 렌즈로 봐도 묶음이
하나뿐일 때만** 건너뛴다 — 유형이 주식 하나뿐이어도 국가가 셋이면 고를 게 있다.

### 9.6 목표 합 100% 초과는 **막는다**

사용자 질문: *"한 비중 바꾸면 나머지 모두 연동돼서 바뀌는 건가?"* 당시엔 아니었다(지금은
축 고정으로 **의도적으로** 상계한다 — §9.2.1). 그런데 예전 동작은 더 나빴다 — 넘겨도 저장되고 **읽을 때** `capToOne` 이 전부를 비례 축소했다.
80% 를 넣었는데 72.7% 로 보였고, 손대지 않은 다른 종목의 목표까지 같이 줄었다.

나머지를 자동으로 줄이는 길(진짜 연동)도 있었지만 택하지 않았다. 한 칸을 고쳤을 뿐인데
손대지 않은 값이 전부 움직이면 "내가 정한 값"이 남지 않는다. **막고 여유를 알려준다** —
줄일 곳은 사용자가 고른다.

```text
저장 거부: "목표 합이 100%를 넘어요. 여기엔 30.0%까지 넣을 수 있어요 — 다른 걸 먼저 줄여주세요."
```

여유는 **고치는 대상만 빼고** 센다(`lib/targetLens.ts:roomFor`). 자기 자신을 포함해
세면 이미 20% 인 종목을 20% 로 다시 저장하는 것조차 막힌다.

`capToOne` 은 남겼다 — 이 검증이 생기기 전에 저장된 값과 손으로 고친 JSON 때문이다.
정상 경로가 아니라 마지막 안전망이다.

### 9.6.1 숫자는 키패드 시트로 넣는다

줄마다 4.5rem 짜리 `<input type="number">` 가 붙어 있었다. 모바일에서 정확히 누르기도
어렵고, 누르면 OS 키보드가 화면 절반을 덮으며 방금 고치던 줄을 가렸다. 사용자 요청:
*"누르면 숫자 입력하는 모달 뜨면 좋겠어."*

새 부품을 만들지 않았다 — 거래 입력이 쓰는 하단 시트 키패드(`components/ui/NumberPad.tsx`)를
그대로 감쌌다(`components/ui/PercentPad.tsx`). 숫자를 넣는 몸짓이 앱 안에서 하나로 통일된다.

```text
  [ 미국 ›   지금 52% · ₩52,000,000        60.0% ]   ← 오른쪽을 탭
                                              ↓
                          ┌──────────────────────┐
                          │   미국 목표비중       │
                          │        60.0%         │
                          │   지금 52% · ₩52M     │
                          │   1  2  3            │
                          │   4  5  6            │
                          │   7  8  9            │
                          │   .  0  ⌫            │
                          │   [    확인    ]     │
                          └──────────────────────┘
```

`확인`·배경 탭·ESC 어느 쪽으로 닫아도 **값이 바뀌었으면 저장한다**(레일의 금액 입력과 같은
규칙). 취소 버튼을 따로 두지 않는 대신 묶음 저장은 되돌리기 토스트가 받쳐 준다.

줄의 **왼쪽(이름 + `›`)은 드릴다운, 오른쪽 알약은 편집**으로 갈라 둔다. 줄 전체를 편집으로
쓰면 그 묶음 안으로 들어갈 길이 사라진다.

### 9.6.2 투자 가능 현금 카드를 지웠다

2단계 아래에 "투자 가능 현금" 카드가 있었다 — 자기 입력칸과 저장/전액쓰기/취소 버튼까지
달고. 사용자 지적: *"얼마 넣을까요에 투자 가능 현금 없어도 되지 않아?"*

맞다. **그 단계가 묻는 게 정확히 그 금액이고, 칸에 이미 채워져 있다.** 카드는 같은 질문을
한 번 더 물었고, 배분에 실제로 쓰이는 건 큰 숫자 칸에 적힌 값이다. 카드에서 정한 값은
그 칸의 기본값일 뿐이었으니, 화면에 둘을 나란히 두면 "어느 게 진짜냐"가 생긴다.

값 자체는 사라지지 않았다. **등기할 때 그때 넣은 금액을 다음 기본값으로 기억한다**
(`savePlan` → `setInvestableCash`). 생활비를 빼두고 싶으면 그만큼 적게 넣으면 되고,
그게 곧 다음번 기준이 된다 — 정하는 화면이 따로 필요 없다.

등기 **뒤에** 저장하는 게 중요하다. 2단계에서 저장하면 `revalidatePath("/allocate")` 가
레일 한복판에서 화면을 다시 그린다.

### 9.6.3 현금을 비중 목록에서 뺐다 — 분모가 엔진과 어긋나 있었다

`planAllocation` 은 처음부터 **증권만**으로 나눴는데(`portfolioValue`), 화면은 목표를
**증권 + 현금** 대비로 보여주고 저장했다. 같은 "주식 45%" 를 화면은 *증권+현금의 45%* 로
말하고 엔진은 *증권의 45%* 로 계산해, 현금이 25% 면 배분액이 의도의 3/4 로 깎였다.

사용자 지적이 그 증상을 짚었다 — *"얼로케이션할 때 현금 비중이 과대계상돼 있어.
비중 조절할 때 현금은 빼주는 게 낫겠어."*

- 1단계 목록에서 **현금 줄을 뺐다.** 분모는 배분 대상 증권이다.
- 합이 100% 가 아니면 목록 아래에 `100%로 맞추기` 가 나온다 — 축 고정을 켜면 합이 안
  변하므로 손잡이가 하나는 있어야 한다(`lib/targetLens.ts:normalizeTargets`).
- 얼마를 현금으로 둘지는 **2단계(넣을 금액)** 가 정한다. 목표로 정하는 게 아니다.
- 통화 현금 목표(`CASH:USD`)는 분모가 **현금**이라 증권의 100% 와 따로 논다.

자세한 근거는 `target-lens-spec-v1.md` §5.10.

### 9.7 최종 화면 구조 (§6 갱신)

```text
/allocate                          레일 1 목표(유형·국가·산업 탭) → 2 금액 → 3 묶음
                                        → 4 순위·배분 → 5 주수 → 도장 ✓   탭바: 1단계만
/allocation                        조회 투자자산(유형 + 현금)
/allocation/financial/[type]       조회 한 유형 안 — 종목/국가/산업 렌즈, 종목 줄에서 편집
/allocation/group/[key]/[label]    조회 유형을 가로지르는 한 묶음(국가·산업), 종목 줄에서 편집
/allocation/cash                   조회 통화별 현금
/allocate/settings · /allocate/plan · /allocate/universe   → 리다이렉트(옛 링크 보존)
```

### 9.8 남은 거친 곳

- `/allocate` 가 산업 태그 backfill 을 켠다(`loadAllocateData({withSectors:true})`).
  멱등이고 채워진 뒤엔 즉시 반환하지만, **끝내 못 채우는 종목은 열 때마다 재시도**한다.
- 통화 현금 목표(`CASH:USD`)도 100% 를 나눠 가진다. 그래서 현금 줄이 40% 로 보여도
  통화에 10% 를 배정해 뒀으면 종목에 넣을 수 있는 여유는 30% 다. 거부 메시지는 정확한
  숫자를 말하지만, 두 숫자가 왜 다른지는 `/allocation/cash` 각주에서만 설명된다.
